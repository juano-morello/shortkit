## 2. The tenancy substrate's actual surface

Everything a new table inherits RLS through:

- `tenantScopedPolicies(table: string): PolicySet` — `apps/api/src/db/rls.ts:57-80`. Returns four DDL statements (ENABLE RLS, FORCE RLS, one `FOR ALL` policy with matching `USING`/`WITH CHECK` on `tenant_id = current_setting('app.tenant_id', true)::uuid`, a privileged-erase `FOR DELETE` policy, and a `tenant_id` index). Table name is validated by `assertTableName` (`apps/api/src/db/rls.ts:37-45`, regex `^[a-z_][a-z0-9_]*$`).
- `TENANT_ID_COLUMN_SQL` — `apps/api/src/db/rls.ts:103-104`: `'tenant_id uuid NOT NULL REFERENCES tenants(id) ON DELETE CASCADE'`, the column every tenant-scoped table declares.
- `redirectReadPolicy(table: 'domains' | 'links'): PolicySet` — `apps/api/src/db/rls.ts:89-100`. Not relevant to item 1; a `FOR SELECT` escape used only by two future link/domain tables.
- **Drizzle Kit generates no policy DDL.** Each schema file's producing TASK appends the RLS statements from `tenantScopedPolicies()` to the generated migration by hand, in the same commit (`apps/api/src/db/rls.ts:6-8`). `pnpm db:check-policies` (`apps/api/scripts/check-policies.mts`) asserts the result against `pg_policies` afterward.
- `withTenantTransaction<T>(tenantId, fn, options?)` — `apps/api/src/tenancy/tenant-context.ts:164-269`. Opens a transaction, runs three `set_config` calls (`statement_timeout`, `idle_in_transaction_session_timeout`, `app.tenant_id`), then `fn(db)`; commits on resolve, rolls back and rethrows on throw. Nesting with the same `tenantId` reuses the outer transaction (no savepoint); nesting with a different `tenantId` throws `TenantContextMismatchError`. `options.afterCommit` queues work (e.g. mail) to run only after COMMIT succeeds — this is the ADR-0002-mandated place for any third-party network I/O, never inside `fn`.
- `tenantId` MUST be a uuid (`assertUuid`, `apps/api/src/tenancy/tenant-context.ts:308-314`) before it reaches `set_config`; it is validated from exactly three sanctioned sources per the docblock at `tenant-context.ts:158-162`: the `tid` JWT claim (authenticated routes — not built), `crypto.randomUUID()` in application code (signup, uninvited branch — not built), or a capability token's routing prefix (ADR-0021 — not built).
- `tenantDb(): TenantDb` and `currentTenantId(): string` — ambient reads via `AsyncLocalStorage`, throw `TenantContextMissingError` outside an active transaction (`apps/api/src/tenancy/tenant-context.ts:317-339`).
- **No `databaseDb` or unbranded client is ever exported.** `apps/api/src/db/client.ts` exports only `databaseTransaction`, and its enumerated sanctioned callers (as of this commit) are `withTenantTransaction`, `withRedirectRead` (not yet built), `privilegedTenantEraser` (not yet built) and `assertRuntimeRoleCannotBypassRls` (`apps/api/src/db/client.ts:11-23`).
- `assertRuntimeRoleCannotBypassRls()` — `apps/api/src/db/rls.ts:137-178`. Boot-time guard checking three properties of the connected role (not superuser, not `BYPASSRLS`, owns zero tables in `public`), throws if any fail.

**`registerTenantScopedSurfaces()` does not exist anywhere in the repository** — I searched `apps/api`, `.sdlc`, and the whole tree for that identifier and found zero matches. If this is expected substrate, it was not confirmed to exist; do not describe it as shipped. The nearest real analogue is `tenantScopedPolicies()` above plus the isolation harness's manual `n()` registration (`apps/api/test/isolation/registrations.ts`), which is test-only and unrelated to production wiring.

## 3. The one migrated table, migration setup, and cost of adding tables

- `tenants` (`apps/api/src/db/schema/tenants.ts:14-21`): `id uuid PRIMARY KEY` (app-supplied, never DB-generated — signup mints the id and opens the tenant transaction under it before inserting, per ADR-0021), `name text NOT NULL`, `created_at timestamptz NOT NULL DEFAULT now()`. It carries `id`, not `tenant_id`, so it does NOT use `tenantScopedPolicies()` — it gets a bespoke four-policy set (self-select, self-update, self-insert, privileged-erase; no ordinary DELETE policy by design, F-005) hand-appended in `apps/api/drizzle/0000_odd_betty_ross.sql:6-35`.
- Drizzle config: `apps/api/drizzle.config.ts` — schema glob is `./src/db/schema/*.ts` (a glob over the directory, not the barrel — a forgotten `export *` in `schema/index.ts` still produces a correct migration; ADR-0019's cross-check against `information_schema` is what catches a missing barrel export). `out: './drizzle'`. `dbCredentials.url` reads `DATABASE_MIGRATION_URL`.
- Migration commands: `db:generate` = `drizzle-kit generate` (needs no connection). `db:migrate` = `drizzle-kit migrate`, run as `DATABASE_MIGRATION_URL` (role `shortkit_migrator`, which owns the tables) — never `DATABASE_URL` (role `shortkit_app`, which owns nothing and cannot run DDL) (`apps/api/drizzle.config.ts:9-11`).
- Exactly one migration exists: `apps/api/drizzle/0000_odd_betty_ross.sql` (35 lines, `tenants` table + its 4 hand-appended policies).
- `apps/api/test/support/rls-fixture.ts:73,349` creates a SECOND table, `rls_fixture_rows` (constant `RLS_FIXTURE_TABLE`), entirely at test time inside the isolation harness — it is not part of the Drizzle schema or any migration, it exists only inside the isolation integration suite's own setup/teardown, built to exercise `tenantScopedPolicies()` generically. It is what the roadmap's "two tables: `tenants` and `rls_fixture_rows`" line (`.sdlc/roadmap.md`) refers to, and it is not a real product table.
- **Cost of adding a second and third real table**: write the Drizzle schema file, add its barrel export to `apps/api/src/db/schema/index.ts`, run `db:generate`, hand-append the `tenantScopedPolicies(table)` output (or the bespoke set, if the table is a cascade root like `tenants`) into the generated SQL in the same commit, run `db:check-policies` to verify against `pg_policies`, and register it in the isolation harness (`apps/api/test/isolation/registrations.ts`, via `n()`) or `apps/api/test/isolation/coverage.ts` fails the build for an unregistered table. Also: F-239 below — new tables are writable by `shortkit_app` via `ALTER DEFAULT PRIVILEGES` before any policy exists for them, so table creation and policy-append are not safely separable in time.

## 7. Gotchas

- **No deploy target exists.** ADR-0030 ("No deploy target is chosen for the API, and the repository stops implying one") is accepted. The trust-boundary decisions in ADR-0040 follow from this: `Fly-Client-IP` cannot be trusted today because there is no platform hop stripping/setting it, and the compose stack publishes the API directly on `127.0.0.1:3001` with no proxy in front — `curl -H 'Fly-Client-IP: ...'` fully controls the "trusted" header in the only environment that runs today (`.sdlc/foundation/design/adr-0040-trusted-client-address-is-declared-and-may-be-absent.md:22-29`). `CLIENT_TRUST_BOUNDARY` / `BFF_TRUST_BOUNDARY` are declared properties that may be absent, and absence means "assert nothing, resolve no principal" — the *opposite* polarity from `MAIL_TRANSPORT`, where absence selects a safe sender rather than asserting nothing (`mail-sender.md:74-79`). An auth design that reflexively trusts a header will be building on ground ADR-0040 explicitly says is not there yet.
- **`Dockerfile:83` sets `ENV NODE_ENV=production`** unconditionally in the image `docker compose up` runs. This is exactly the F-386 shape: any future binding keyed on `NODE_ENV` (auth cookie flags, mail transport, DNS resolver — F-400 names the same trap for custom domains) will silently select production behavior on a laptop. The ruled fix pattern is a dedicated declared env var per capability (`MAIL_TRANSPORT` for mail), not `NODE_ENV`.
- **CI gate is three jobs feeding one gate check, not four:** `quality`, `integration`, `compose` all `needs:` into `gate`, which asserts all three succeeded (`.github/workflows/ci.yml:382-397`). `quality` alone runs audit/lint/typecheck/test/build/AC-113 secret-scan/stub-drift/contract-drift as sequential steps — if "four checks" was expected, verify what specifically was meant; the three-job/one-gate structure is what's in the file today.
- **Test layout, three tiers:** `pnpm test` = `vitest run` against `**/*.spec.ts` only (`apps/api/vitest.config.ts:10`), no Docker, no network. `pnpm test:integration` = separate config, `**/*.int-spec.ts` only, `fileParallelism: false` because every integration file shares one database and one fixture that drops/recreates tables per test (`apps/api/vitest.integration.config.ts:53-70`) — a file named like an integration spec but missing the exact `.int-spec.ts` suffix silently never runs, and the config asserts against that (`vitest.integration.config.ts:27-45`). The isolation suite (`apps/api/test/isolation/cross-tenant-isolation.int-spec.ts`) is a third tier in the same integration run, with its own registration mechanism (`n()` in `apps/api/test/isolation/registrations.ts`) that a new tenant-scoped table must be added to or the build fails on an unregistered table.
- **The isolation harness's coverage is bounded by imagination, not completeness**, per Juano's 2026-08-11 ruling recorded in the roadmap: three consecutive audit rounds each found a new statement shape the harness didn't check (unqualified writes, owner-column writes, refusal-scored-as-pass). Five more shapes (`ON CONFLICT DO UPDATE`, `MERGE`, eviction, cascade/trigger, `SELECT ... FOR UPDATE`) are named but not yet built into the harness (F-341). This initiative will add the second and third real tables the harness has ever covered — treat "the isolation suite passes" as bounded, not as proof.
- **The stub-drift gate only enforces `apps/web/**` today** (F-403, roadmap) — it will start defending `apps/web/src/lib/session/session.ts` the moment TASK-012's web session file lands, but nothing under `apps/api/src/auth/**` or `apps/api/src/mail/**` is gated by it yet, so an implementer who copies the stale `apps/api` mail stub gets no automated warning (this is exactly the F-401 mechanism).
- **`packages/contracts/src/roles.ts` already exists and is shipped, not deferred** — do not plan a TASK to "create the role types"; several of its functions are stubbed (`asTenantRole`, `asWorkspaceRole`, `roleRank`, `tenantRoleRank` all throw), but the types, brands, and rank tables are real and importable today.
- **`registerTenantScopedSurfaces()` — could not find this symbol anywhere in the repo.** If it was expected to already exist, it does not; verify the name/expectation before relying on it in Refine.
